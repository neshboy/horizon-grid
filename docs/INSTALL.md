# Install / Local Setup

> **Superseded.** This page predates [QUICKSTART.md](QUICKSTART.md) (zero-to-first-lookup
> walkthrough) and [DEPLOYMENT.md](DEPLOYMENT.md) (Docker Compose + Kubernetes deployment
> reference), which are now canonical — kept here for history only.

How to run HORIZON GRID locally with Docker Compose.

## Prerequisites

- **Docker Desktop** (with Compose v2) — runs all services: Postgres, Redis,
  Neo4j, OpenSearch, the FastAPI backend, Celery worker + beat, and the
  Next.js frontend.
- **[Ollama](https://ollama.com) installed on the host**, with a model
  pulled that fits comfortably in your GPU's VRAM (a model that spills to
  CPU/mmap is dramatically slower per response), e.g.:

  ```bash
  ollama pull llama3.2:3b
  ```

  This is the default AI backend (`AI_BACKEND=ollama`, no API key, no
  cloud cost) — the backend container reaches it via
  `OLLAMA_BASE_URL=http://host.docker.internal:11434` (already set in
  `docker-compose.yml`). Without a model pulled, provider summaries and the
  final assessment degrade to "AI summarization unavailable" but the rest
  of the platform (provider fetch, correlation, dashboard) still works.
- *Optional — alternative AI backends:* set `AI_BACKEND` to `bedrock`,
  `gemini`, or `anthropic` in `.env` and fill in the matching credentials
  (AWS IAM + Bedrock model access, a Gemini API key with quota, or an
  Anthropic API key with credit, respectively) if you'd rather use a cloud
  model than a local one.
- *Optional:* free-tier API keys for the real (non-stub) provider
  connectors — VirusTotal, AbuseIPDB, AlienVault OTX, NVD, and a single
  abuse.ch Auth-Key shared by URLhaus/ThreatFox/MalwareBazaar. The platform
  runs and streams results without any of these; providers without a key
  simply report `not_configured` (see Troubleshooting).

## Steps

1. **Clone the repository.**

   ```bash
   git clone <repo-url> ioc-intel-platform
   cd ioc-intel-platform
   ```

2. **Create your `.env` file.**

   ```bash
   cp .env.example .env
   ```

3. **Fill in `.env`:**
   - `OLLAMA_MODEL` — set to whatever you pulled above (check the exact tag
     with `ollama list`); leave `AI_BACKEND=ollama` and `OLLAMA_BASE_URL` as
     the defaults for local Docker Desktop use.
   - `JWT_SECRET_KEY` — replace the placeholder with a long random string
     (used to sign access/refresh tokens).
   - Any provider keys you have (`VIRUSTOTAL_API_KEY`, `ABUSEIPDB_API_KEY`,
     `OTX_API_KEY`, `NVD_API_KEY`, `ABUSECH_AUTH_KEY`, etc.). Leave the rest
     blank — see Troubleshooting for what happens when a key is missing.
   - If you'd rather use a cloud AI backend, set `AI_BACKEND` to `bedrock`,
     `gemini`, or `anthropic` and fill in the matching credentials.

4. **Build and start everything.**

   ```bash
   docker compose up --build
   ```

   This starts `postgres`, `redis`, `neo4j`, `opensearch`, `backend`,
   `celery_worker`, `celery_beat`, and `frontend` (see
   `docker-compose.yml`).

5. **Migrations run automatically.** The `backend` service's command is:

   ```
   sh -c "alembic upgrade head && uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload"
   ```

   so the database schema is brought up to date every time the backend
   container starts — there is no separate migration step to run by hand.

6. **First-run registration.** No seed admin user exists. Register the
   first user via the API (or once the frontend exposes a registration
   form):

   ```bash
   curl -X POST http://localhost:8000/api/v1/auth/register \
     -H "Content-Type: application/json" \
     -d '{"email":"you@example.com","password":"change-me","full_name":"Your Name"}'
   ```

   The **first** user ever registered is automatically granted the `admin`
   role; every registration attempt after that is rejected with `403
   Forbidden` (`app/api/routes/auth.py`) — every account after the first
   admin must be created by that admin via `POST /api/v1/admin/users` or
   the Administration page. Then log in via `POST /api/v1/auth/login` to
   get an access/refresh token pair (see `docs/API.md`).

7. **Access the app.**
   - Frontend: <http://localhost:3000>
   - Backend interactive API docs (Swagger UI, auto-generated by FastAPI):
     <http://localhost:8000/docs>
   - Backend health check: <http://localhost:8000/health>

## Troubleshooting

**AI summaries show "AI summarization unavailable" / final assessment shows "unknown" with a generation-error caveat**
The configured AI backend didn't respond successfully. For the default
Ollama backend, check:

1. Is Ollama actually running on the host? `curl http://localhost:11434/api/tags`
   should list your pulled model(s).
2. Does `OLLAMA_MODEL` in `.env` exactly match a model `ollama list` shows?
3. Is the model too large for your GPU's VRAM? A model that spills to
   CPU/mmap can take minutes per response instead of seconds — check
   `docker compose logs backend` for `RuntimeError: Ollama did not respond
   within Xs`, and either switch to a smaller model or raise the timeout in
   `app/ai/ollama_client.py`.

For the Bedrock backend specifically, `AccessDeniedException` means your
IAM principal has valid credentials but hasn't been granted access to the
model in `BEDROCK_MODEL_ID` — in the AWS Console, go to **Bedrock → Model
access** in the region set by `AWS_REGION` and enable it (one-time,
per-account/per-region, can take a few minutes to propagate). Also confirm
the model has a Regional availability entry for your region on its model
card — some models (e.g. newer Claude versions) only support the `global.`
cross-region inference profile from certain regions, not the plain model ID.

**A provider shows status `not_configured`**
This is expected and by design, not a bug — `BaseProvider.run()` returns
`not_configured` for any provider whose `requires_key` is `True` but whose
API key isn't set (see `app/providers/base.py`). To enable it:

1. Add the corresponding `*_API_KEY` (or URL/credential pair) to `.env`.
2. Recreate the backend container so it picks up the new `.env` value —
   **`docker compose restart backend` is not enough**; Compose only re-reads
   `.env` when a container is created/recreated, not on a plain restart:

   ```bash
   docker compose up -d backend
   ```

3. Confirm via `GET /api/v1/providers/health` that `configured` is now
   `true` for that provider.

**`GET /api/v1/providers/health` or lookups return 401/403**
All lookup and provider-health endpoints require a bearer token
(`Authorization: Bearer <access_token>` from `/auth/login`). A 403 on
`lookup:create` means the account's role lacks that permission — only
`admin` and `analyst` roles can create lookups; `viewer` is read-only (see
`ROLE_PERMISSIONS` in `app/models/user.py`).

**Frontend can't reach the backend**
By default the frontend no longer needs any configuration for this: `lib/api.ts`'s
`getApiUrl()` derives the backend URL at runtime from whatever host you used
to load the page (`window.location.hostname`) plus `NEXT_PUBLIC_BACKEND_PORT`
(defaults to `8000`) -- this is why the exact same build works from
`localhost`, `127.0.0.1`, or a LAN IP with no rebuild. If requests are still
going to the wrong host, check whether `PUBLIC_API_URL` was set explicitly
in `.env` (it should normally be empty) -- an explicit value there always
wins over auto-detection, which is the right behavior for a reverse-proxy
setup but will look like this bug if it's set by mistake.

## Accessing From Another Device on Your Network

The installer creates a Windows Firewall rule (Private networks only) for
the platform's ports and the Setup Wizard detects this machine's LAN IP
address, both automatically -- no configuration needed for the common case.
After installing, the wizard's Finish page and the app's Manage Providers →
Network Access tab both show a LAN URL you can open from any other device
on the same network. If a second device can't connect:
- Confirm both devices are on the same network, and that network is set to
  **Private** in Windows (Settings → Network & Internet) -- the firewall
  rule intentionally does not open the ports on Public networks.
- If your router assigned this machine a new IP address (common after a
  reboot or router restart), re-run **Configuration** from the Start Menu
  to re-detect it and refresh the LAN URL shown in the app.
